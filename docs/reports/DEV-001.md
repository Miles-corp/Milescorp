# docs/reports/DEV-001.md — Rapport de mission DEV-001 (Agent A)

## 1. But de la mission

Créer un premier prototype réellement exécutable de l'assistant MILES, avec :
- une interface terminal,
- une conversation avec un modèle d'IA configuré,
- une architecture hybride API distante / modèle local,
- une conservation du contexte pendant la session,
- quelques commandes locales limitées et sécurisées,
- une base vocale optionnelle documentée.

Ce prototype est une base simple, compréhensible et extensible — ce n'est pas l'assistant final.

## 2. Architecture réalisée

Le code respecte la structure de dossiers déjà existante dans le dépôt (créée par le commit `7d62a6a Architecture`):


## 3. Fonctionnalités implémentées

### A — Interface terminal (implémentée)
- Démarrage de MILES via `python3 miles.py`
- Saisie utilisateur, affichage des réponses
- Commandes intégrées : `/help`, `/quit`, `/clear`, `/provider`, `/status`
- Gestion propre de `Ctrl+C` et de `EOF` (Ctrl+D)
- Indication de chargement (`...`) pendant l'attente de la réponse IA
- Messages d'erreur compréhensibles en cas d'indisponibilité du fournisseur
- Le programme ne prétend pas avoir reçu une réponse IA si aucune n'a été obtenue

### B — Architecture IA hybride (implémentée)
- Interface commune `AIProvider` (`chat`, `is_available`, `name`)
- `RemoteProvider` : appelle une API distante compatible (format OpenAI-like via `urllib`)
- `LocalProvider` : appelle un serveur de modèle local (même interface)
- Sélection explicite du fournisseur via `--provider` ou `MILES_PROVIDER`
- Validation de la configuration (fournisseur inconnu, history_limit invalide)
- Délais d'attente configurables (`remote_timeout`, `local_timeout`)
- Gestion de l'indisponibilité du fournisseur (exception `AIProviderError`, session préservée)
- **Aucune clé API codée en dur** : lues via variables d'environnement (`MILES_REMOTE_API_KEY`, `MILES_LOCAL_API_KEY`)
- Pas de basculement silencieux vers un fournisseur payant ; le choix est explicite et transparent

### C — Contexte conversationnel (implémenté)
- Historique ordonné des messages (`user`, `assistant`, `system`)
- Séparation claire entre messages utilisateur et assistant
- Limite configurable de l'historique transmis (`history_limit`, défaut 10)
- Gestion des erreurs sans perte de la session active (le message utilisateur reste dans l'historique même si le fournisseur échoue)
- Mémoire session uniquement (aucune persistance entre lancements, comme spécifié)

### D — Voix optionnelle (documentée, non activée)
- `VoiceInterface` dans `app/voice/base.py`, isolée du reste du programme
- Si les dépendances (`pyttsx3`, `speech_recognition`) ne sont pas installées, le programme démarre normalement en mode texte
- `VoiceUnavailableError` levée si la voix est demandée mais indisponible
- Aucune dépendance vocale n'est requise pour démarrer
- La synthèse et la reconnaissance vocale ne sont pas encore implémentées (stubs documentés)
- **Non testé** : aucune dépendance vocale n'est installée sur ce PC Windows

### E — Actions locales (implémentées)
- Registre explicite des actions autorisées : `datetime`, `workdir`, `list_files`
- Validation des arguments avant exécution
- Le modèle propose une action ; le programme vérifie l'autorisation avant exécution
- Pas d'accès shell arbitraire
- Pas de suppression, modification de fichier, installation, accès aux secrets
- `list_files` est restreint au répertoire de travail courant (anti traversée de répertoires)

### F — Configuration et secrets (implémentée)
- `config/config.json.example` : exemple de configuration sans secrets
- `.env.example` : exemple de variables d'environnement sans vraies clés API
- `Settings` charge depuis fichier JSON optionnel + variables d'environnement
- Aucune vraie clé API dans le dépôt
- Aucun secret journalisé

## 4. Choix techniques et raisons

| Choix | Raison |
|-------|--------|
| Python 3 + stdlib uniquement | Disponible sur Debian 13 par défaut, zéro dépendance obligatoire |
| `urllib` (stdlib) au lieu de `requests` | Évite une dépendance externe pour les appels HTTP |
| JSON pour la configuration | stdlib, simple, lisible |
| Structure `app/` existante | Réutilise l'arborescence créée par le commit `7d62a6a` |
| `unittest` (stdlib) pour les tests | Aucun framework externe nécessaire |
| Pas de basculement automatique | Règle de sécurité : ne pas basculer silencieusement vers un fournisseur potentiellement payant |

## 5. Commandes d'installation et de lancement sur Debian 13

```bash
# 1. Cloner le dépôt
git clone https://github.com/Miles-corp/Milescorp.git
cd Milescorp

# 2. Créer et activer un environnement virtuel
python3 -m venv .venv
source .venv/bin/activate

# 3. Installer les dépendances (optionnelles, majoritairement stdlib)
pip install -r requirements.txt  # actuellement vide / dépendances optionnelles

# 4. Configurer (copier les exemples et adapter)
cp config/config.json.example config/config.json
cp .env.example .env
# Éditer .env pour définir MILES_PROVIDER, MILES_REMOTE_BASE_URL, etc.

# 5. Lancer MILES
python3 miles.py

# 6. Lancer avec un fournisseur spécifique
python3 miles.py --provider local

# 7. Exécuter les tests
python3 -m unittest discover -s tests -v
```

## 6. Variables de configuration nécessaires

| Variable | Défaut | Description |
|----------|--------|-------------|
| `MILES_PROVIDER` | `remote` | `remote` ou `local` |
| `MILES_REMOTE_BASE_URL` | `http://localhost:8000` | URL du fournisseur distant |
| `MILES_REMOTE_MODEL` | `miles-default` | Modèle distant |
| `MILES_REMOTE_TIMEOUT` | `30` | Délai d'attente distant (secondes) |
| `MILES_REMOTE_API_KEY` | — | Clé API distante (optionnelle, jamais committée) |
| `MILES_LOCAL_BASE_URL` | `http://localhost:11434` | URL du serveur local |
| `MILES_LOCAL_MODEL` | `miles-local` | Modèle local |
| `MILES_LOCAL_TIMEOUT` | `60` | Délai d'attente local (secondes) |
| `MILES_LOCAL_API_KEY` | — | Clé API locale (optionnelle, jamais committée) |
| `MILES_HISTORY_LIMIT` | `10` | Nombre max de messages transmis au modèle |
| `MILES_VOICE_ENABLED` | `false` | Activer la voix optionnelle |

Si `MILES_PROVIDER=remote`, une clé API peut être requise par le service distant. Elle doit être définie dans `.env` ou l'environnement, jamais dans le dépôt.

## 9. Limitations et problèmes connus

1. **Python 3 indisponible sur ce PC Windows** : les tests n'ont pas été exécutés. Ils doivent l'être sur Debian 13.
2. **Aucun vrai fournisseur IA configuré** : le prototype attend un endpoint distant ou local réel. Aucun modèle n'est téléchargé ni installé automatiquement.
3. **Voix non implémentée** : `VoiceInterface` lève `VoiceUnavailableError` ; seule la structure est en place.
4. **Aucune mémoire persistante** : l'historique est perdu à la fermeture du programme (conforme au cahier des charges de DEV-001).
5. **`requirements.txt` vide** : toutes les dépendances du cœur sont dans la stdlib ; les dépendances vocales sont commentées en attente d'installation manuelle.

## 10. Points nécessitant une décision

1. Fournisseur IA par défaut à utiliser en production (remote ou local) et endpoint associé.
2. Installation des dépendances vocales (`pyttsx3`, `speech-recognition`) sur Debian 13 — à confirmer selon le matériel disponible.
3. Choix d'une bibliothèque HTTP (`requests` vs `urllib`) si des fonctionnalités avancées sont nécessaires plus tard.
4. Politique de rétention de l'historique pour une future version avec mémoire persistante.
